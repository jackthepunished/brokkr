# 0011 — Authentication: OIDC/JWT clients + mTLS workers

- **Status:** accepted
- **Date:** 2026-06-28
- **Deciders:** Brokkr maintainers

## Context

Phase 4 §16 task 8: "mTLS between workers ↔ control plane. OIDC or static API
tokens for clients." Today the control plane is unauthenticated: any client can
call `Execute`/CAS/`ActionCache`, and the tenant id is a *client-asserted*
`x-brokkr-tenant` header (ADR 0010), which is spoofable. Worker↔control TLS
flags exist (`--tls-cert/--tls-key/--tls-client-ca`) but client certificates
are not required even when a client CA is configured.

## Decision

**Client auth via OIDC/JWT bearer tokens; worker↔control via mTLS; auth is the
authoritative tenant source.**

### Client authentication — JWT bearer

- Clients present `authorization: Bearer <jwt>` in gRPC metadata. The control
  plane validates the JWT's signature, `exp`, and (when configured) `iss` /
  `aud`, and reads the **tenant** from a configured claim (default `tenant`).
- The authenticated tenant is **authoritative** — it overrides the
  `x-brokkr-tenant` header from ADR 0010, closing that spoofing gap. (When auth
  is disabled, the header remains the source, as today.)
- Enforced by a tonic interceptor / per-handler check in `brokkr-control` on the
  client-facing services (`Execution`, `ContentAddressableStorage`,
  `ActionCache`, `ByteStream`, `Capabilities`). The internal `WorkerService` is
  authenticated by mTLS, not client tokens.
- **Open mode when unconfigured.** If no JWT verification is configured, the
  control plane allows calls and logs a prominent `AUTH DISABLED — NOT FOR
  PRODUCTION` warning (mirrors the existing TLS-disabled warning). Keeps local
  dev + the in-process fixtures working unchanged.
- **First increment scope:** validate against a *configured* decoding key (a
  PEM public key for RS*/ES*, or an HMAC secret) — i.e. a static key / static
  JWKS. **Live JWKS-URL discovery + fetch/cache is deferred** to a follow-up
  (it needs an HTTP client; not worth the dep surface for the first cut).

### Worker ↔ control — mTLS

- When `--tls-client-ca` is set, the control plane already loads it as the
  client-cert root; this milestone ensures client certificates are actually
  *required/verified* on the worker-facing path and documents the posture.
  (Deriving a worker identity from the cert is a later nicety.)
- **Enforcement shipped in issue #139.** The first cut loaded the CA but did
  not require a client cert, and the worker-facing `WorkerService` shared
  one listener with the JWT-gated client services. That combination
  silently rejected every worker's `batch_update_blobs(stdout, stderr)`
  with `UNAUTHENTICATED` (the worker has no bearer token). The fix is to
  bind a second gRPC listener on a separate port dedicated to
  `WorkerService`, configured with `client_auth_optional=false` so the
  presented client cert is mandatory. `ContentAddressableStorage` is
  co-located on that same worker port so workers can still upload
  stdout/stderr — sharing the same `RedbCas` instance as the
  JWT-gated client port gives a single content-addressable store across
  both paths. The four REAPI services (CAS client surface, `ActionCache`,
  `Capabilities`, `Execution`) stay on the JWT-gated client port. The
  control plane **refuses to start** with a clear error in the
  contradictory combinations (`--single-port` + `--auth-jwt-*`, or
  `--auth-jwt-*` without `--tls-client-ca`); see
  `crates/brokkr-control/src/main.rs` (`Args::validate_auth_flags`) and
  the integration suite at
  `crates/brokkr-control/tests/split_port_cluster.rs`.

### Dependency

- JWT validation needs a vetted crypto/JWT library — hand-rolling signature
  verification is a non-starter. Proposed: **`jsonwebtoken`** (de-facto Rust JWT
  crate; >1k downloads, actively maintained, MIT; RS/ES/HS algorithms; no
  network I/O of its own). Pulls `serde_json` (already in-tree) + a crypto
  backend (`ring`, already in-tree via rustls/tonic TLS). Confirm before adding
  (CLAUDE rule 6).

## Alternatives considered

- **Static API tokens** (bearer token → tenant allowlist). Simpler, no crypto
  dep, but long-lived shared secrets and no standard rotation/expiry. Rejected
  in favour of JWT per the owner's call; the JWT path subsumes it.
- **Deny-all when unconfigured** (secure by default). Rejected for the default
  to avoid breaking fixtures/e2e and local dev; operators opt into enforcement
  by configuring verification (same model as the TLS flags).
- **Live OIDC discovery (JWKS URL) now.** Deferred — needs an HTTP client and
  JWKS caching; static key validation covers the core auth need first.

## Consequences

- **Positive:** Real client authentication; tenant identity becomes
  trustworthy (closes the ADR-0010 gap); standard short-lived-token model.
- **Negative:** Adds a crypto/JWT dependency; full OIDC (JWKS discovery,
  rotation) is a follow-up, so the first cut needs keys configured out-of-band.
- **Neutral:** Open-mode default means auth is opt-in; production must
  configure it (loudly warned otherwise).
